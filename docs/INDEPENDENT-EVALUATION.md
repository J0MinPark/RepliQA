# RepliQA 판정 평가와 독립성

2026-09-18. 기존 개발용 55개 사례와 분리하여 10개 새로운 여정의 정상·결함 쌍 20개를 작성했다. 실행 전에 HTML, 계약, 정답, 실행 코드와 엔진 해시를 manifest.json에 고정하고 각 사례를 새 브라우저 컨텍스트에서 두 번 실행했다. 클라우드·외부 AI 요청은 하지 않았다.

독립성의 한계: 구현자와 평가 작성자가 같다. 제3자 독립 감사나 실제 고객 사이트의 표본 평가가 아니다. 20개 사례 또는 반복 실행 40건으로 일반 정확도를 주장하지 않는다.

## 최초 관측 — 수정 전 결과 보존

- 정상 10개: 10개 통과, 오탐 0개.
- 결함 10개: 9개 failed, 1개 inconclusive. 결함 검출률 9/10; 확인 불가인 결함도 미검출에 포함한다.
- 선택 직후 원상 복귀하는 라디오 버튼 결함은 Playwright의 check 동작 오류에서 중단되어 명시적인 기능 불일치로 분류되지 않았다. 잘못 통과시키지는 않았지만 결함 검출의 한계였다.
- 원본은 evaluation/results/beta-holdout-20260918-first에 보관한다. 공개용 사본은 [최초 평가 기록](evidence/beta-release/holdout-first.json)에 있으며 고정한 계약·HTML·소스 해시와 전체 관측을 포함한다.

## 수정 후 — 이제 회귀 사례

Playwright가 클릭 완료 후 체크 상태 불일치를 명시한 경우에만, 네이티브 체크박스/라디오의 상태를 세 번 다시 읽어 실패 근거로 남긴다. 쓰기 동작은 반복하지 않는다. 비활성·가림·타임아웃·중복 대상은 이 규칙으로 실패 판정을 만들지 않는다.

동일 20개 × 2회에서 기대 판정과 일치했다. 이 결과는 수정 검증이며 새로운 독립 평가 결과가 아니다. [수정 후 회귀 기록](evidence/beta-release/holdout-regression.json).

## 제3자 평가 실행 절차 — 아직 미수행

1. 검토자가 개발용 사례를 재사용하지 않고 업무 계약·정상 앱·결함 앱을 준비한다. 최초 작업 목표는 정상 100개·결함 100개이며 표본 충분성을 보장하는 숫자가 아니다.
2. 정상 결과와 주입 결함을 별도 검토자가 확인한다. 실행 전에 소스·데이터·정답 해시를 고정하고 구현자에게 정답을 숨긴다.
3. 고정 엔진 버전으로 실행하고, 원래 정답과 모든 결과를 공개 가능한 합성 데이터로 보관한다. 판정 실패를 보고 정답을 바꾸지 않는다.
4. 고유 사례와 반복 실행을 분리한다. 오탐, 결함 미검출(확인 불가 포함), 거짓 통과, 미실행, 완료율, 범주별 검출률·신뢰구간을 보고한다.
5. UI 기능, AI 계획 생성, 시각 판단, 실제 클라우드 운영을 별도 축으로 평가한다. 이번 20개 평가는 AI 발견 능력이나 Cloudflare 네트워크 격리를 검증하지 않는다.
6. 수정에 사용한 사례는 회귀 세트로 옮기고, 다음 독립 평가에는 새로운 미공개 사례를 사용한다.

고객 공개 판단에서 미검출을 숨기거나 전체 검사 정확도 100%로 홍보하지 않는다.
