# RepliQA 사용법과 현재 검사 범위

RepliQA는 실제 Chromium에서 페이지를 열고, 지정한 동작과 결과를 확인하는 QA 실행 도구다. 현재 클라우드판은 LLM 없이 동작한다. 자연어 한 문장만으로 사이트 전체의 업무 규칙과 모든 여정을 알아내는 QA 에이전트는 아니다.

접속: https://repliqa-pilot.repliqa-cloud.workers.dev

## 처음 실행하기

1. 초대 키로 접속한다. 검사할 사이트는 운영자가 먼저 등록해야 한다. 키를 리포트나 공개 저장소에 넣지 않는다.
2. `검사 방식`에서 `자동 기본 점검` 또는 `여정 검사`를 고른다.
3. 기본 점검은 사이트와 시작 경로를 지정하면 된다. 현재 페이지의 HTTP 응답, 내용, 제목, 문서 언어, 이미지, 입력 이름, 링크 속성, 접근성 자동 규칙 등을 확인한다. 모든 링크를 방문하거나 업무 기능을 검사하지는 않는다.
4. 여정 검사는 동작 순서, 최종 경로, 정상 문구를 지정한다. 동작 대상은 화면의 이름, 중간 결과 검증 대상은 CSS 선택자다. 최대 12단계를 실행한다.
5. 권한과 정상 결과를 검토하고 `검사 실행`을 누른다. `검사 내역`에서 단계, 판정 근거, 마스킹한 화면, 미검사 범위를 확인한다.
6. `계획 파일 저장`으로 계획을 내려받아 다음 배포에서 재사용한다. 입력값은 제외되므로 불러온 뒤 다시 입력하고 검토한다.

## 첫 여정 예제 — 실제 결제가 없는 장바구니

등록 사이트가 RepliQA 예제 사이트일 때 다음과 같이 구성한다.

| 항목 | 값 |
|---|---|
| 시작 경로 / 최종 경로 | `/demo` / `/demo` |
| 첫 동작 | 선택(select), 대상 `수량`, 값 `2` |
| 다음 동작 | 클릭(click), 대상 `장바구니 담기` |
| 중간 결과 검증 | 문구 확인(assertText), 대상 `#cart-result`, 값 `장바구니 2개 · 합계 24,000원` |
| 최종 문구 | `장바구니 2개 · 합계 24,000원` |
| 결과 영역 | `#cart-result` |
| 결과 변경 확인 | 체크 |

클릭 자체의 성공뿐 아니라 수량과 합계가 맞게 바뀌었는지 확인하는 예제다. 실제 결제는 발생하지 않는다. 설명란에 요구사항만 쓰고 검증 조건을 생략하면 그 요구사항을 자동으로 해석해 모두 검사하지 않는다.

## 결과 읽기

- `passed`: 지정한 조건에서 통과했다. 사이트 전체에 오류가 없다는 뜻은 아니다.
- `failed`: 지정한 조건과 관측 결과가 불일치했다. 요구사항이나 대상 지정이 맞는지도 검토한다.
- `review`: HTTP 오류나 접근성 규칙 등의 검토 후보가 있다. 업무 결함으로 확정한 결과가 아니다.
- `inconclusive`: 차단, 모호한 대상, 접근성 수동 판단, 실행 중단 등으로 판정 근거가 충분하지 않다. 통과나 결함으로 계산하지 않는다. 정확성 평가에서 실제 결함에 대한 확인 불가는 미검출에 포함한다.
- `not_run` / `not_tested`: 중단으로 실행하지 않았거나 검사 범위 밖이다.

클릭·입력·선택·체크, 스크롤, 뒤로/앞으로 이동, 새로 고침, hover와 제한된 키 입력, 문구·값·개수·표시·선택·활성 상태 및 URL 검증을 조합할 수 있다. 동일한 이름의 버튼이 여러 개라면 대상을 특정하지 못할 수 있다.

0.2.5는 HTTP 리디렉션과 WebSocket을 차단한다. 최종 HTTPS URL과 필요한 리소스 호스트를 등록해야 한다. 로그인/SSO, 파일 업로드·다운로드, 실결제, 전체 시각 회귀, 부하 검사, 다중 브라우저·기기 검증은 현재 클라우드판의 완성된 기능으로 제공하지 않는다. 위험 동작의 이름을 차단하지만 모든 업무의 위험을 자동으로 알아내지는 못하므로 합성 데이터와 테스트 권한이 있는 환경을 사용한다.

서비스의 현재 가치는 **반복할 조건이 명확한 브라우저 QA를 실행하고 근거를 남기는 것**이다. 외부 검토자가 확인한 일반 정확도와 실제 팀의 시간 절감 효과는 아직 입증되지 않았다.
